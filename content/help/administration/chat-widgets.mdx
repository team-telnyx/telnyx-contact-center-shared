# Web Widgets

Open **Admin → Web Widgets**. Widget Studio provides the configuration sections and responsive preview from the reference widget project, using native Contact Center authentication, queues, and messaging.

## Prepare the queue and agents

1. Save the queue and agent accounts first.
2. In the queue editor, open **Channels & Utilization**, enable **Chat**, set its maximum and workload percentage, and save the queue with **Save Changes**.
3. Do the same in each eligible agent's user editor. Disable **Voice** for an agent who will work without a phone.
4. Assign agents to the queue and activate their queue membership. Agents open **Agent Desktop** and set their status to **Available**.

Both the agent and queue must enable Chat. The smaller maximum wins. An agent with a maximum of 2 receives at most 2 chat offers/assignments across all queues and browser sessions, even if a queue permits 5. Pending offers, active work, and wrap-up each occupy one slot. The larger queue/agent workload percentage applies, and all occupied work must fit the agent's workload budget. Voice is exclusive.

The footer saves channel settings together with the other user or queue settings. Changing a limit revalidates unaccepted offers; accepted conversations continue to completion.

## Create and publish

1. Click **New widget** or **New**, enter a unique name, and create the draft.
2. Under **Channels → Available channels**, enable Messaging and/or Voice and select **Widget AI assistant**. Configure the queue and routing allowlist under **Handoff → AI chat handoff routing**. Widgets without an assistant use **Handoff → Direct chat routing**. For video conferences, enable **Voice & Video Call** and follow [Video calls with AI and Vision](#video-calls-with-ai-and-vision); video has its own assistant selection and fallback queue.
3. Under **Targeting**, enter the allowed embedding origins, including the scheme and port where applicable. Use an exact origin such as `https://shop.example.com` or an HTTPS wildcard such as `https://*.example.com`.
4. Configure dimensions, appearance, launcher, messages, handoff timeline, attachments, triggers, heads-up messages, rules, language, and accessibility. Use the device preview to check placement and sizing.
5. Click **Publish**. Publication validates the current draft and queue configuration, creates or reuses the installation's shared chat handoff tool, and attaches it to the widget assistant. Copy the installation script from **Embed** into the customer website.

Drafts autosave valid changes. **Save draft** retries a failed save. A conflicting editor must reload and review the latest revision before saving. Publication makes an immutable revision and opens a new draft; existing conversations retain the configuration with which they started.

**Clone** copies the complete draft and uploaded preview backgrounds. **Edit** changes the administrative name. **History** shows publications and audit events; **Restore to draft** restores a prior publication for review before publishing it again.

Disabling the widget stops new bootstrap/session admission. An already connected visitor can continue the current conversation until it ends or the inactivity timeout is reached. An origin removed from the publication can no longer use its old session.

## Agent controls

Agents accept or decline offers in **Agent Desktop**. Each chat has its own message history, reply draft, typing indicator, emoji picker, and attachment controls. **End chat** closes the conversation and starts its wrap-up. Select a wrap-up code and click **Complete** to release the slot. A configured wrap-up deadline also releases it automatically. Customer inactivity abandons waiting work or starts wrap-up on an accepted chat.

Attachment types and sizes come from the widget publication. Files are stored with the conversation and require authorized access. Delivery status confirms storage by Contact Center; it does not claim the other participant has read the message.

## AI chat handoff

When a visitor requests a human, the assistant calls the managed **Contact Center Chat Handoff** webhook tool. Contact Center queues the same conversation, copies the AI transcript, and provides the agent with the assistant's summary, reason, intent, and sentiment. Subsequent visitor messages go to Contact Center, and late AI replies are suppressed after transfer.

The first widget publication creates one shared tool per Contact Center installation. Later publications reuse that tool and attach it to every associated assistant without replacing their other tools or instructions. A failed tool setup prevents publication; retry **Publish** after resolving the provider error. The tool is also available in **AI Assistants → Tools Library** for manual assignment. It operates only on Contact Center web chat sessions with private integration context; attaching it does not enable handoff from arbitrary voice or external conversations.

In **Handoff**, select a default Chat queue and the allowed queues. **Use all Chat-enabled queues** clears the restriction. With no explicit selection, all enabled Contact Center queues with Chat enabled are eligible. The assistant can choose an eligible queue by name. Otherwise, `routing.queue` in the host-page context selects a queue, followed by the widget default or the sole eligible queue. An invalid or ambiguous destination produces a failure notification and leaves the AI conversation active so the assistant can clarify and retry. Host-page context cannot bypass the allowlist. Eligibility also respects the current publication if its allowlist has changed.

The configured timeline shows waiting, an offer assigned to an agent, acceptance, and disconnection. A failed transfer shows its failure message without claiming the visitor is waiting in a queue. Queueing does not require an available agent; the visitor waits until a qualified agent with free capacity is available. Disabling a widget prevents new AI handoffs while existing human conversations can drain.

Start a new chat after this feature is first enabled so the provider conversation receives the private handoff context. The widget generates this context on the server; no additional public embed snippet or secret is required.

## Current delivery boundary

The widget supports native human chat, AI assistant messaging with optional image input, AI-to-queue chat handoff, AI assistant voice widgets, and video conferences with human/AI participants and optional Vision. The shared chat handoff tool applies to chat; video uses its own conference handoff and fallback queue.

## AI channels

In **Channels → Available channels**, the Messaging and Voice switches share one **Widget AI assistant** picker. Search by name or ID. The selection belongs to the widget revision, is saved for both channels, and remains assigned when either channel is disabled and re-enabled. Draft saving and publication reject conflicting assistant IDs. Voice without a native Telnyx avatar uses the AI Agent Library and requires unauthenticated web calls in the assistant's Widget settings. **Voice → Web Calls** contains the media region setting for those calls.

### Images in AI chat

Select an image-capable **Widget AI assistant**, enable **Allow images in AI chat** under **Channels**, then **Publish**. The application verifies the primary and fallback models. Chat uploads use the model's image input directly; a Vision tool alone does not enable uploads and is not required for this chat path. Use still PNG, JPEG or WebP images, at most three per message and 5 MiB per image. After handoff to a human, that chat's attachment policy also applies.

Start a new chat after publication. Existing chats retain their original revision, and **Persist session** can restore that old chat on refresh. End the conversation and choose **Start new conversation**, or test in a fresh private browsing session. If the widget reports **Images for the AI assistant are disabled**, check the published chat image switch and session revision before changing video deployment settings.

### Voice-call avatars

Enable the avatar under **Voice** and choose a provider. **Telnyx** is the preferred default for new widget configurations. Existing explicit HeyGen and Anam selections remain unchanged. Selecting Telnyx offers six avatars and three backgrounds; the catalog displays official Telnyx portrait previews, which remain visible in the voice panel until the first video frame appears.

Telnyx avatars require a Telnyx TTS voice and the assistant's main version. Publishing saves the avatar and background on that assistant. Widgets sharing an assistant must agree on both settings; publication rejects conflicting choices. Use a separate assistant for a different avatar. Publication does not change the assistant's voice. Changes made directly to its avatar settings require republishing the widget.

Native Telnyx avatar calls use the authenticated AI Assistant WebSocket API through the Contact Center relay and receive synchronized audio and video over WebRTC. They do not require unauthenticated web calls. The existing microphone, speaker, text input, transcript, expansion and end-call controls remain available. Telephone transfers, DTMF, **Keep assistant on call**, and the Web Calls media-region selector do not apply to these conversations. A nonfatal avatar failure after the call starts continues with audio only; a setup failure ends the attempt and allows a fresh call.

The server requires `TELNYX_API_KEY` and a browser-reachable streaming relay. The avatar route shares the existing relay listener: `/widget-avatar`, normally exposed as `/ws/widget-avatar`. `WS_BASE_URL` or `STREAMING_WS_URL` can specify its public base; HTTPS pages require WSS. The API key remains on the server. Widget session tokens authenticate the socket's first frame and never appear in its URL.

The preview device selector fills the right panel width. Its orientation control is on the following row.

## Video calls with AI and Vision

The deployment administrator must first complete [Video AI instance setup](/help/setup#video-ai-and-vision). The video runtime is included in Contact Center; custom or older deployments may still need updated Docker security options and recording storage.

1. Prepare a source assistant whose primary and fallback models are verified for buffered Vision. For an avatar with Vision, use a compatible Telnyx TTS voice. GPT Live does not support buffered Vision. Publication rejects incompatible workflow, telephone transfer, delegation and custom client tools.
2. Enable **Video** in the fallback queue's **Channels & Utilization**. For human handoff, enable Video for eligible agents, configure their capacity and activate queue membership.
3. Enable **Channels → Available channels → Voice & Video Call**. Open **Video**, set **Start the video call with → AI assistant**, select **Video queue / fallback queue**, and choose **Video AI assistant**. For human-first calls, choose queue/agent routing and enable **Allow agents to invite an assistant** instead.
4. Optionally enable **Show a Telnyx avatar**, choose its avatar/background, and set **AI after the agent joins**. The assistant can use Vision with audio-only participation as well.
5. Set **Vision** to **Uploaded images only** or **Uploaded images and live video**. Add the Vision tool to the source assistant, or enable **Add Vision tool on publish** to add it to the dedicated video profile. Verify additional assistants allowed for invitations too.
6. For live Vision, choose **Allowed Vision sources**, **Vision source selection**, **Preferred camera**, and **Let the assigned agent control Vision**. Enable **Screen sharing** if visitors should share their screen. Configure **Record calls** separately.
7. Click **Publish**, then **Check published assistant profiles**. Confirm **Published profile is up to date**. Video publication creates a managed profile while preserving the source assistant's voice/chat settings. Changes to the source require publishing again.
8. Open **Test the published video widget**. End any previous call and reload before starting the new one. The embedded website must be allowed under **Targeting** and use HTTPS for camera/microphone access (localhost is suitable for development).

During the call, each participant must explicitly allow AI to see their own camera or screen. Browser media permission alone does not grant AI access. Only one selected, authorized source is analyzed at a time. Automatic selection uses an authorized screen or the preferred camera; manual selection pauses when its source disappears. Allow about 10.5 seconds when switching sources. Owners can revoke their source consent at any time.

Verify an audible reply, moving avatar video when enabled, and an accurate answer about a harmless test image or selected camera/screen. A static portrait, Studio preview or healthy web endpoint does not prove that Video AI is connected. **The video assistant service is unavailable** requires checking worker readiness/capacity and instance configuration; adding a Vision tool does not fix a failed browser runtime.

The **Allow images in AI chat** switch is independent of the Video Vision settings. Enabling either one does not enable the other.

## Agent and queue settings

The user editor separates **Account Settings**, **Channels & Utilization**, **Queue Assignments**, and **Skills & Proficiency** into cards. The queue editor places **Channels & Utilization** between **Queue Settings** and **Routing Settings**. The footer button saves all cards in one database transaction; there is no separate utilization save button.

File attachments remain available in native Contact Center chat. AI chat also accepts images when explicitly enabled as described above. A message with an uncertain provider result remains pending and is not automatically sent again.

## Anonymous session admission

New sessions are limited to 10 per minute per widget and client address, with a separate 600-per-minute widget safety cap. Successful retries and session resumption do not consume additional slots. The database stores a keyed hash of the address, not the raw address.

The ingress must append verified peer addresses to `X-Forwarded-For` and prevent direct public access to Next.js. Set `WIDGET_TRUSTED_PROXY_HOPS` to the number of trusted ingress hops (default 1). Client-supplied leading entries are ignored. Missing or invalid addresses share a restricted fallback bucket. Use the same widget signing secret across application nodes.

## Co-browsing

In Widget Studio → **Co-browsing**, enable page sharing and choose the permitted entry points. Configure the pairing-code lifetime, privacy preset, additional mask selectors and blocked content. Enable **Allow agent to request control** only when assisted interaction is intended, then publish.

Viewing needs visitor consent. Control needs separate consent and the agent's `cobrowse:control` permission, in addition to request/view access. The default Agent role does not include control. The site owner must explicitly mark eligible links, safe buttons and fields with `data-cobrowse-control`. Password/payment fields, private targets and form submissions remain blocked. All input values stay masked in the replay. Co-browsing is live and is not recorded.

Test both approval and refusal, masking, code expiry, disconnect, transfer and consent revocation using the Studio test page. Source-site script/WebSocket policies must allow the widget. See the [agent procedure](/help/agent/cobrowsing).

## Test page and publication checks

Open **Delivery → Test page** for the signed-in widget test host. Use synthetic data to test navigation, attachments, masking, allowed controls and published media settings. For video, also check recording configuration, waiting playlist, agent admission and supervision; a Studio preview alone does not verify those runtime paths.

Changes require publication before a new visitor session uses them. Existing sessions retain their original revision. Inspect **History** when comparing a report with the current draft, and begin a fresh session after changing AI, image or video settings.
